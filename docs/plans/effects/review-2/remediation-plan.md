## Project Principles

1. Prefer the cleaner long-term architecture over compatibility with existing implementation details: prioritise correctness, internal coherence, technical debt reduction, and maintainability, and when a local compatibility-preserving fix conflicts with a cleaner architecture, choose the cleaner architecture unless a concrete limitation prevents it.
2. API-breaking changes are acceptable when they lead to a better end state.
3. When a concrete limitation forces a fallback from the preferred approach, document the limitation, the trade-offs, and the fallback before adopting it.
4. Make illegal states unrepresentable. Work out the valid states and transitions first, then encode them using algebraic data types (e.g., enums, structs, newtypes) and type-level constraints, so invalid combinations cannot be constructed, instead of admitting them and guarding against them with defensive run-time checks. Express the valid states and transitions with tools like state diagrams and decision tables; an exhaustive decision table over a product of sum types is a total pattern match. When a concrete limitation of the language or type system prevents encoding a constraint directly, fall back to the closest approximation it allows, backed by a checked boundary or a documented invariant, and record the limitation per principle 3.
5. Parse, don't validate (Alexis King). Reject malformed input at the boundary and turn it into a precise type, so the pure core can trust the data it holds rather than re-checking it or adding fallbacks deeper in. Validation lives once, at the boundary (the effectful shell); everything inside operates on already-valid types.
6. Make failure and absence explicit, and pattern matches total. Represent failure and absence as data the caller must engage with (Result and Option, not nulls, exceptions, or silent defaults), and prefer exhaustive matches with no catch-all wildcard where a missing case would be a bug, so adding a variant forces every decision point to be revisited.
7. Ground decisions and implementations in evidence. Before a recommended approach is adopted and built out as a complete feature, validate it with a small proof-of-concept that demonstrates it builds and produces the expected outputs. If validation fails, adopt the next-best candidate and validate that too, repeating until an approach is validated or the candidate approaches are exhausted; if they are exhausted, surface the impasse for a decision rather than forcing through an unvalidated approach.

## Documentation Protocol

This plan intentionally does not use a separate section for previously resolved decisions. Resolved or adopted decisions are folded into the implementation plan as concrete steps. This keeps the document from accumulating stale decision history while still making the intended work clear. Correspondingly, when an entry in the Open Questions section is resolved, it is removed from that section entirely and its decision is folded into the relevant Implementation Step; it is not retained in the Open Questions section as a compressed "resolved, see step X" pointer, since such pointers re-accumulate the stale decision history this protocol exists to avoid. When no entries remain, the Open Questions section simply states that none are open.

During implementation, this document should be kept up to date by indicating, for each of the implementation steps, what their current status is.

Status convention: each work item carries a `Status:` line (`not started`, `in progress`, `blocked on <item or question>`, `decided`, `complete`, or `rejected with reason`). While an item is in progress, its individual numbered steps are annotated in place (for example `2. (done) ...`). When a work item in the Implementation Steps section is decided or completes, the item itself remains (it is the work to be done) but its recommendation text is compressed in place to the adopted decision plus a pointer to the evidence or implementing commits. This in-place compression applies only to a surviving Implementation Steps work item; it is not a licence to leave a compressed pointer in the Open Questions section, where a resolved entry is removed outright per the rule above.

### 5. Substrate unification: one closure-storage-parameterised substrate

Findings: architecture.md section 3.6 (do all six wrappers earn their keep); prior-reviews-crosscheck.md section 2 item 7 (the W3 capability audit's undecided half).

Decision (adopted): gate G3 / POC-8 ([foundation-sweep/poc-8-findings.md](foundation-sweep/poc-8-findings.md)) shows substrate unification is feasible (go), superseding the earlier "shrink or formalise the wrapper matrix" framing. The six erased wrappers collapse: the substrate type, its interpreter, and its `Clone` instance become one `Run<Store: ClosureStorage, A>` over an associated stored-closure type, with the per-`Store` `Clone`/`Send + Sync` bounds carried on the substrate's inherent methods (which a fixed trait method signature could not carry). Recorded boundary: closure construction stays per-`Store` (the `Store::Stored` projection is not injective, so generic construction cannot infer `Store`), so smart constructors and per-effect injection stay generated (item 7); POC-8b ([foundation-sweep/poc-8b-findings.md](foundation-sweep/poc-8b-findings.md)) confirms `bind`/`map` join that per-`Store` construction surface (their bodies move the captured continuation for Box and clone it for Rc/Arc), without moving the substrate type, interpreter, or `Clone` off their single definitions. The per-pointer matrix question is answered by this collapse: the closure-pointer axis becomes one parameterised substrate, with `Store` ranging over the closure-storage brands. The erased-versus-Explicit axis is a separate, orthogonal axis the `Store` parameter does not touch (`'static` + `dyn Any` + O(1) `CatList` bind versus non-`'static` + concrete payloads + recursive bind); the erasure axis was resolved by the POC-11 spike ([foundation-sweep/poc-11-findings.md](foundation-sweep/poc-11-findings.md)) to B: two `Store`-parameterised forms (six wrappers to two), the erased form (O(1) `CatList` bind, `'static`) and the concrete form (O(N) bind, non-`'static`), reusing the existing `Free` and `FreeExplicit` spines. C2 (one substrate, internal erasure) is ruled out because the erased O(1) path forces `A: 'static` (`Box<dyn Any>`) and stable Rust cannot select it conditionally; approach A (drop non-`'static`) was eliminated by the catalog audit. So "one parameterised substrate" holds per form, two forms in total.

This work is item 4 step 5.

Status: decided (substrate unification go, via FS-1); implementation folded into item 4.
