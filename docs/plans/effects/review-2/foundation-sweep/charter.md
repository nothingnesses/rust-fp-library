# Effects Foundation Sweep: Spike Charter

This charter plans a feasibility investigation into rebuilding the effects subsystem's foundation. It supersedes the recommendation recorded in [remediation-plan.md](../remediation-plan.md) item 12 (which recommended writing a dual-row decision record and holding a prototype in reserve): the decision has been taken to investigate the alternatives directly, by prototype, at full foundation scope. The sweep also produces the evidence that remediation items 8 (one effect-spec surface and order-independent dispatch), 13 (brand-capability and wrapper-matrix scope), and 14 (wrapper-family generation) depend on, so its conclusions feed back into all four items.

This is a charter, not a findings document. It defines the designs to compare, the proof-of-concept (POC) ladder that produces the evidence, the decision gates, and the assessment rubric. No production code and no POC code is written under this charter until it is reviewed. POC findings will land as sibling documents in this directory and their conclusions will be folded back into the relevant remediation items.

## Project Principles

- API-breaking changes are acceptable when they lead to a better end state.
- The project prioritises correctness, internal coherence, technical debt reduction, maintainability and long-term architecture over compatibility shims for existing implementation details.
- When a local compatibility-preserving fix conflicts with a cleaner architecture, choose the cleaner architecture unless a concrete limitation prevents it.
- If such a limitation forces a fallback, document the limitation, the trade-offs, and the fallback before adopting it.

## Documentation Protocol

This plan intentionally does not use a separate section for previously resolved decisions. Resolved or adopted decisions should be folded into the implementation plan as concrete steps. This keeps the document from accumulating stale decision history while still making the intended work clear.

During implementation, this document should be kept up to date by indicating, for each of the POC steps, what their current status is. As each POC completes, its row in the ladder is updated (status plus a one-line outcome and a link to its findings document), each decision gate records the choice taken and why, and any conclusion that settles a remediation item is folded back into that item.

## Why a foundation sweep, and why now

The four axes below are entangled: each is foundational, each is currently implemented in a way the review flagged as costly, and a rebuild of any one touches the code the others live in. Investigating them together avoids re-deriving the same machinery three times and avoids committing to a row design before knowing whether the higher-order and substrate decisions that build on it are feasible.

The single most important grounding finding, which reframes the feasibility prior, is that the library already defunctionalises rank-2 natural transformations: [natural_transformation.rs:97](../../../../../fp-library/src/classes/natural_transformation.rs#L97) defines `NaturalTransformation<F, G>` as a trait whose method `fn transform<'a, A: 'a>(&self, fa: F::Of<A>) -> G::Of<A>` is generic over `A`, and [free.rs:1218](../../../../../fp-library/src/types/free.rs#L1218) threads it through `fold_free`. Heftia's higher-order machinery needs exactly this shape (`hfmap :: (m ~> n) -> e m ~> e n`), which stable Rust cannot express as a closure but can express as a struct with a generic method. So the deepest theoretical risk in a faithful unified-row port is already solved in this library's idiom; the remaining risks are the more mundane ones the POCs below target.

Other grounding facts confirmed before writing this charter:

- Multi-arity `Kind`s are first-class: [bifunctor.rs:89](../../../../../fp-library/src/classes/bifunctor.rs#L89) and the scoped boundary code both use `Of<'a, A, B>`. A carrier-parameterised effect kind is therefore expressible.
- There is no existing type-level order or boolean marker convention in `fp-library/src`. The order classification machinery is genuinely new code and is the subject of the first POC.

The `data-effects` package (heftia's effect-definition and core-class layer) is now available as a local reference, and reading its source corrected and sharpened several assumptions. The relevant facts, from `data-effects-core/src/Data/Effect.hs`, `Data/Effect/HFunctor.hs`, and `Data/Effect/OpenUnion.hs`:

- An effect has kind `(Type -> Type) -> Type -> Type` (it is parameterised by the carrier `f` and the result). Each effect carries three independent type-family classifications, not one: `OrderOf e :: EffectOrder` (`FirstOrder` or `HigherOrder`), `FormOf e :: EffectForm` (`Polynomial` or `Exponential`), and `LabelOf e` (a per-effect label type used as the dispatch and tagging key). Supporting classes are `FirstOrder`, `HFunctor`, `PolyHFunctor`, and `Weave`.
- `FirstOrder e` is formally `OrderOf e ~ 'FirstOrder` plus `forall f g a. Coercible (e f a) (e g a)`: a first-order effect's representation does not depend on the carrier, so it can be retyped across carriers for free. Heftia exploits this with `coerceFOEs = unsafeCoerce` gated by a `FOEs es` class (all remaining effects first-order). The Rust analog is stronger: a first-order effect brand whose `Of` projection ignores the carrier parameter makes the FOE retype a safe type-level identity, with no `unsafe` needed where Haskell needs `unsafeCoerce`. This is a green flag for Axis 1 and for `expand` over a unified row.
- `HFunctor` is `hfmap :: (forall x. f x -> g x) -> ff f a -> ff g a`, exactly the defunctionalised `NaturalTransformation` shape the library already has. Higher-order effects implement it (for example `Local f a` maps to `Local f (phi a)`).
- `FormOf` separates polynomial higher-order effects (the carrier appears only in covariant field positions; `Local`, `WriterH`'s `Listen`/`Censor`, `Catch` are all polynomial) from exponential ones (the carrier appears in a function or negative position, for example continuation-capturing effects). `PolyHFunctor` is the safety property that prevents resources escaping a scope. Polynomial higher-order effects are the mechanical case for elaboration and weave; exponential effects (CC/Shift and unlift-style operations) are out of scope for this sweep and remain a later design round.
- The open union `Union es f a` stores an integer membership index plus a runtime order tag and dispatches by index match, and the membership constraint `type e :> es` is resolved by `LabelOf` (label-keyed), not by position. So heftia's own dispatch is label-keyed and reifies order at runtime for branching, which is direct support for Axis 3's brand-keyed direction.
- Heftia's primary interpret loop (`heftia/src/Control/Monad/Hefty/Interpret.hs`) requires `FOEs es` on the remainder and uses `coerceFOEs` to relay unmatched first-order effects; the `Weave` class is a separate mechanism, explicitly the "Effect Handlers in Scope" weave used by `fused-effects` and `polysemy`, for threading a context functor through a higher-order scope with mtl-like (order-dependent, conditionally transactional) semantics. Heftia therefore offers two higher-order mechanisms, not one, which changes Axis 2 below.

## The four axes under investigation

Axis 1: Row representation. Current: dual rows, `Run<R, S, A>` with a first-order row `R` and a scoped row `S`, dispatched by the `Node` enum ([architecture.md](../architecture.md) section 1, section 3.1). Alternative: a single unified row `E` of effect brands, each carrying an order marker, matching the referenced heftia's current design. Cost of the status quo: every program type and alias and error carries two row parameters; first-order-only programs (the common case) drag `CNilBrand`/`ScopedNil` everywhere; row machinery (`expand`, `weaken`, interpose, narrowing) exists in first-order and scoped variants.

Axis 2: Higher-order effect (HOE) mechanism. This is a three-way choice, sharpened by the `data-effects` reading. The current local mechanism is boundary frames plus per-wrapper carrier and residual dispatch protocols, the largest single source of internal complexity ([architecture.md](../architecture.md) section 1 item 5, and the W8 audit). Heftia offers two alternatives, both of which a unified row enables and both of which would delete the boundary-frame subsystem and most of the five result-polymorphic protocol traits:

- Elaboration: rewrite each HOE into first-order effects (via the existing interpose machinery) before algebraic handling, requiring an `FOEs`-style "remainder is all first-order" property at the point of algebraic handling. This is the cleaner, more predictable mechanism (interpretation stays a structural rewrite, order-independent for the cases it covers), and is heftia's primary interpret path.
- Weave: thread a context functor through the higher-order scope ("Effect Handlers in Scope", the `fused-effects`/`polysemy` approach, shipped in `data-effects` as the `Weave` class). It handles strictly more (it does not require elaborating the HOE away first) at the cost of mtl-like, order-dependent semantics. Notably, that order-dependence is exactly the branch-local-versus-global behaviour the review flagged as currently inexpressible with the cell-based runners ([refactoring-opportunities.md](../refactoring-opportunities.md) R5): weave is one principled way to obtain it, so this axis and the R5 semantics gap are connected.

Elaboration is the architectural prize and the primary bet; weave is the heftia-blessed fallback for higher-order effects that resist clean elaboration, and is itself strictly better than retaining boundary frames (it is the documented upstream mechanism rather than a bespoke local one). The sweep scopes both to polynomial higher-order effects; exponential effects (CC/Shift, unlift) are a separate later design round.

Axis 3: Membership and handler dispatch. Current: positional cons-lists walked in lock-step with the row, requiring the row and handler macros to sort entries by a syntactic structural key, which produces the spelling-sensitive footgun ([refactoring-opportunities.md](../refactoring-opportunities.md) R1, item 8). Alternative: brand-keyed type-level dispatch (search the handler list by effect brand), which makes handler-list order irrelevant and removes the handler-side sort. A unified row interleaves first-order and higher-order effects by sort key, which makes positional alignment strictly worse, so brand-keyed dispatch is likely near-mandatory for a unified row rather than merely desirable. This is also the heftia-faithful choice: heftia's membership constraint `type e :> es` is resolved by `LabelOf` (label-keyed), and the same label mechanism is how heftia expresses tagged duplicate effects. Brand-keyed dispatch therefore unifies remediation items 8 (the footgun) and 11 (tagged effects): the effect brand is the natural label, and a tag is a wrapper that changes the label.

Axis 4: Substrate and closure storage. Current: six hand-maintained wrapper families over six substrates (erased and explicit, each Box/Rc/Arc), 60 to 75 percent mutually identical, plus per-effect brand siblings keyed by closure storage ([architecture.md](../architecture.md) section 3.6; [refactoring-opportunities.md](../refactoring-opportunities.md) R2, R3). Alternative: one substrate parameterised by a closure-storage brand, with one brand per effect parameterised the same way. The wrapper-matrix table in `types/effects.rs` records that Brand-level class unification is blocked by per-result `Clone` (Rc) and `Send + Sync` (Arc) projection bounds that trait method signatures cannot carry; the hypothesis this sweep tests is that a concrete parameterised substrate can carry those bounds on its inherent methods (which can have per-call where-clauses that trait methods cannot), even though the Brand-level classes cannot.

A fifth concern, the result-polymorphic handler protocol (the five `RunFirstOrder*` traits), is treated as a consequence rather than an axis: those traits exist to serve boundary-frame result polymorphism, so if Axis 2 resolves toward elaboration most of them disappear without separate investigation.

## Candidate end-state designs

These are coherent points in the cross-product of the axes, used as the targets the POCs evaluate. The baseline is included so the rubric has a control.

- FS-0 (baseline, control). The current design: dual rows, boundary frames, positional dispatch, six wrappers. No work; scored only for comparison.
- FS-1 (north star). Unified row + elaboration + brand-keyed dispatch + single parameterised substrate. Maximum debt reduction (deletes boundary frames, the protocol traits, the scoped-row machinery, and the six-wrapper duplication; collapses the brand siblings). Maximum risk: every axis must resolve favourably.
- FS-2 (pragmatic hybrid). Unified row + brand-keyed dispatch + single parameterised substrate, with higher-order effects handled by weave (heftia's `Weave`) rather than elaboration. The fallback if elaboration (Axis 2) fails for some higher-order effects but the row, dispatch, and substrate unifications hold. Weave still deletes the boundary-frame subsystem (it is the upstream mechanism, not a bespoke one) and accepts mtl-like order-dependent semantics, which doubles as a principled route to the R5 branch-local-versus-global behaviour. Retaining today's boundary frames under a unified row is the further fallback (FS-2b) only if both elaboration and weave prove infeasible.
- FS-3 (facade stepping stone). Unified user-facing surface via a type-level partition that splits the one row back into today's `Node<FO, HO>` internally; everything else unchanged. Lowest risk, lowest reward: delivers the signature-noise win and a single row parameter immediately while deleting no internals. Useful as an incremental ship even if FS-1/FS-2 are later adopted.

The substrate unification (Axis 4) is separable: it can be adopted with any of FS-1/FS-2/FS-3, or deferred. The POCs keep it isolated (Tier E) so the row decision does not depend on it.

## POC ladder

Principle: isolate each load-bearing risk as the smallest prototype that answers a specific question, run the cheap shared risks first, gate before the expensive bets, and only build an end-to-end slice for the design that survives. All POCs target the default single-wrapper path first to isolate the row, dispatch, and HOE questions from the substrate axis; the substrate axis is tested separately in Tier E. The POC harness, file location, and crate-access level are decided per Open Questions item 6 (a per-POC hybrid of standalone prototypes and public-API integration tests), and POC code hygiene per item 11 (a dedicated spike branch or worktree); `trybuild` (a dev-dependency in both crates) backs the compile-fail cases where the question is about error quality. A Tier-0 step captures the FS-0 baseline metrics before Tier A (item 9). None of the POC code is production code; all of it is removed or promoted after the decision, while the per-POC findings documents are the durable artifacts.

POC-4 and POC-5 each carry two arms, run in preference order: an elaboration arm (rewrite the higher-order effect into first-order effects, the FS-1 mechanism) and, if elaboration cannot reproduce the semantics, a weave arm (thread a context functor through the scope via the defunctionalised `NaturalTransformation`, the heftia `Weave` mechanism, the FS-2 mechanism). POC-5's result-shape-changing case (`listen`/`censor`) is the one that discriminates the arms, because it is precisely what forced today's boundary/carrier split. Both arms target polynomial higher-order effects only; exponential effects are out of scope here.

## Decision gates

- G1, after Tier A, B, C (the cheap, shared POCs). Decide: is FS-3 (facade) viable as an immediate increment, and do the unified row plus brand-keyed dispatch hold well enough to pursue FS-1/FS-2? If POC-0 or POC-3 fails outright, the unified row is infeasible and the sweep falls back to keeping dual rows (and item 12 reverts to its approach A, the decision record). If POC-1 passes but Tier D later fails, FS-3 is the shippable result.
- G2, after POC-5 (the critical gate). Decide the higher-order mechanism in order of preference: elaboration (FS-1), then weave (FS-2), then retained boundary frames (FS-2b). If POC-4 and POC-5 reproduce the heftia semantics by elaboration, FS-1 is on the table and the boundary subsystem is deletable. If elaboration fails for the result-shape-changing case (`listen`/`censor`), POC-5's weave arm decides whether weave reproduces the semantics instead; if it does, the sweep targets FS-2 (still deleting boundary frames). Only if both fail is the limitation recorded per the project principles and boundary frames retained under the unified row (FS-2b).
- G3, after Tier E. Decide substrate unification go/no-go, which settles remediation item 13's approach C (can the matrix collapse) and rescopes item 14 (what, if anything, still needs generation). Independent of G2.
- G4, after Tier F. Write the overall recommendation back into remediation items 8, 12, 13, and 14, with the rubric scores and the chosen design.

## Assessment rubric

Each surviving design is scored against FS-0 on:

1. Builds on stable Rust with no nightly features.
2. Higher-order semantics correct on the heftia suite (especially the listen/censor and State-with-Catch ordering cases).
3. Signature noise: does a first-order-only program shed the second row parameter; typical error-message length for a missing handler.
4. Machinery line-count delta versus FS-0: does it delete the boundary-frame subsystem, the protocol traits, the scoped-row machinery, the six-wrapper duplication, the brand siblings.
5. Migration cost: how much of the effect catalog, the macros, and the wrapper matrix must change.
6. Performance shape: per-layer dispatch overhead and per-bind allocation versus FS-0 (POC-10).
7. Effect on the positional-sort footgun (item 8): eliminated, improved, or unchanged.
8. Composability of the axes: does adopting one axis force or preclude another.

## Open Questions, Decisions, Issues and Blockers

1. Resolved. Heftia's `data-effects` package is now available as a local reference and has been read; its mechanics (three classification type families, the `FirstOrder` Coercible law, `HFunctor`, `Weave`, label-keyed `Union` membership) are folded into the grounding facts and Axis 2 and Axis 3 above. A sub-question remains for later: confirming which specific higher-order effects are `Exponential` (carrier in negative position) versus `Polynomial`, since the sweep scopes only polynomial effects; this is a reading task on the `data-effects` effect modules, not a blocker for Tier A through D.
2. POC-5 (elaborating a result-shape-changing HOE such as `listen` without boundary frames) is the load-bearing unknown for the entire elaboration prize. Its outcome decides FS-1 versus FS-2 at gate G2. No mitigation other than running it early.
3. Brand-keyed dispatch (POC-2) inference quality at scale is unproven; type-level search can degrade error messages. To be assessed against rubric item 3 on a multi-effect row, not just the two-effect POC.
4. Substrate unification (Tier E) interacts with remediation item 13's matrix-scope decision: if item 13 concludes the Explicit or erased family should be dropped, the substrate POCs should target the reduced set. Sequencing: POC-7 provides evidence for item 13 rather than waiting on it, so they are run together.
5. Whether FS-3 (facade) is worth shipping as an interim even if FS-1/FS-2 is the eventual target, given it deletes no internals and would itself be replaced. Decide at G1 with the partition POC's cost in hand.

The following six items were raised after the `data-effects` grounding pass, in a review specifically for blockers that must be settled before any POC is written. Each is settle-able now; the recommendations are proposed for approval, and once accepted they unblock Tier A.

6. POC harness, file location, and crate-access level. The charter's first draft said POCs live as `fp-library/tests/poc_*.rs`. That is only partly workable: those are integration tests over the public API, and several POCs need machinery the public API does not expose. Confirmed facts: `trybuild` is a dev-dependency in both crates; the existing `tests/poc_*.rs` are public-API integration tests; `Free`/`FreeExplicit`, `Kind`/`Apply!`/`impl_kind!`, and the closure-storage classes (`classes::pointer`) are public; but `TypeErasedValue`, `Continuation`, `transform_raw`, and the raw-step machinery are `pub(crate)` and unreachable from `tests/`.
   - Approaches: (a) standalone self-contained prototypes, each file hand-rolling the minimal substrate and coproduct it needs, depending on nothing from the crate; (b) integration tests over the public API (`tests/poc_*.rs`), using the real `Free`, `Kind`, and closure classes but limited to the public surface; (c) in-crate unit tests or a `cfg`-gated scratch module with full `pub(crate)` access.
   - Trade-offs: (a) isolates the type-system question, fastest, but does not prove composition with the real substrate and re-implements a mini `Free`; (b) proves real composition for the public surface but cannot reach internals that POC-6 and any raw-step interaction need; (c) can test anything but pollutes the crate and risks prototype code being mistaken for production.
   - Recommendation: a per-POC hybrid. Type-system-technique POCs (POC-0 order marker, POC-1 partition, POC-2 brand-keyed dispatch) as standalone prototypes (a), since they prove a technique, not an integration. Substrate-composition POCs (POC-3, POC-6, POC-7, POC-8) as public-API integration tests (b), restricted to `Free::{lift_f, resume, fold_free, hoist_free, bind, map, pure}` and `classes::pointer`. A POC drops to in-crate unit tests (c) only if it provably cannot be expressed over the public API, and that necessity is itself recorded as a finding about the public surface.
   - Reasoning: matches each probe to the smallest harness that answers its question, keeps the cheap classification tier decoupled from the 35k-line system, and turns "needs internals" into signal rather than hiding it. If many POCs fall to (c), that is direct evidence that the public substrate API is too thin for the new foundation, which is worth knowing before committing.

7. Coyoneda wrapping in the unified row. The current first-order rows wrap each effect in `CoyonedaBrand` so any effect type is a `Functor` over its continuation for free; heftia's `Union` carries an analogous Coyoneda ("koi") witness. The unified row must decide whether to keep that.
   - Approaches: (a) uniform Coyoneda wrapping of every effect (first-order and higher-order); (b) no wrapping, with effects implementing `Functor` (and higher-order effects `HFunctor`) directly, generated by the effect macro.
   - Trade-offs: (a) zero per-effect `Functor` boilerplate and matches the proven existing approach, at the cost of one allocation/indirection per lifted operation; (b) removes that overhead but requires a generated `Functor` impl per effect and makes the row brand the bare coproduct.
   - Recommendation: fix the feasibility tier to uniform Coyoneda (a) to remove a variable, and revisit (b) in the integration tier where POC-10 can measure whether dropping Coyoneda is worth the per-effect `Functor` boilerplate.
   - Reasoning: the wrapping choice is a performance/boilerplate trade, not a feasibility blocker; pinning it to the known-good option keeps the early POCs focused on the genuine unknowns (classification, dispatch, higher-order mechanism).

8. Reconcile POC-6 (widening) and POC-7 (substrate) with the prior W1 and W8 spikes. `review-1/w1-row-embed-spike.md` already concluded that row widening must be a representation-aware structural traversal (not `unsafeCoerce`, not a `hoist_free`/`NaturalTransformation` wrapper), specifically because default `Run`'s boundary frames need raw-step access; `review-1/w8-consolidation-feasibility.md` concluded the per-wrapper scoped plumbing is about 83 percent mechanical and gated generation behind triggers.
   - Approaches: (a) treat the sweep as greenfield and re-derive widening and generation; (b) read both spikes first and frame POC-6/POC-7 to build on or explicitly refute them.
   - Trade-offs: (a) risks redoing settled analysis and missing the boundary-frame constraint; (b) costs a re-read but anchors the new POCs in prior evidence.
   - Recommendation: (b). Add a pre-step to Tiers D and E to re-read W1 and W8, and frame POC-6 around the falsifiable hypothesis that a unified, boundary-frame-free row removes W1's raw-step requirement, making `expand` expressible over the public `fold_free`/`hoist_free` after all.
   - Reasoning: the unified row's central simplification (no boundary frames) may invalidate W1's hardest constraint; testing that as a stated claim turns a structural simplification into concrete evidence instead of rediscovering the dual-row result.

9. Capture the FS-0 baseline metrics before the sweep. The rubric scores designs against FS-0 on machinery line-count and performance, but no baseline is recorded.
   - Approaches: (a) compare impressionistically at G4; (b) capture now, as a Tier-0 step: the line counts of the boundary subsystem, the five protocol traits, and the six-wrapper duplication (with the measurement commands), plus a run of the existing `effect_rows` and `scoped_operations` benches to fix baseline numbers.
   - Trade-offs: (a) no upfront cost but a vague final comparison; (b) a small upfront cost for a quantitative rubric.
   - Recommendation: (b), folded in as a Tier-0 step at the sweep's start; it also refreshes the W8 line counts that item 14 needs.
   - Reasoning: the debt-reduction and performance rows are the point of the rubric; the numbers are cheap to capture once and make every later comparison concrete.

10. Semantic-validation method for standalone prototypes. POC-4, POC-5, and POC-9 are specified as reproducing the heftia suite results, but a standalone prototype lacks the real `Run` API that `run_heftia_semantics.rs` is written against.
    - Approaches: (a) wire the POCs into the real system to reuse the suite; (b) extract the specific expected values (the State-with-Catch ordering pair, the listen/censor pre/post strings) and assert them inline in each POC, citing the suite case mirrored.
    - Trade-offs: (a) reuses the suite but defeats the standalone approach and couples POCs to the production API; (b) keeps POCs standalone at the cost of restating small constant expectations.
    - Recommendation: (b); each higher-order POC restates the concrete expected values inline and cites the mirrored case, self-contained per the project documentation rule.
    - Reasoning: the expected values are small and stable; inline assertions keep the POCs fast and decoupled while preserving traceability.

11. Git hygiene for throwaway POC code. POCs are explicitly removed or promoted after the decision, so committing then deleting them would churn `feat/effects`.
    - Approaches: (a) commit each POC to `feat/effects` and delete on decision; (b) do POC code on a dedicated `spike/foundation-sweep` branch or worktree, promoting only survivors; (c) keep POCs uncommitted in named stashes per the global preserve-exploratory-work guidance.
    - Trade-offs: (a) simplest but pollutes mainline history with throwaway code; (b) keeps mainline clean and preserves the work, at the cost of branch management; (c) lightest-weight but easiest to lose track of.
    - Recommendation: (b). Run POC code on a dedicated spike branch or worktree; commit only the durable artifacts (this charter and the per-POC findings documents) back to `feat/effects`; cherry-pick into production only code that survives the gates.
    - Reasoning: keeps the mainline branch's history free of throwaway prototypes while preserving the work and its findings, matching the global worktree and preserve-exploratory-work guidance.
