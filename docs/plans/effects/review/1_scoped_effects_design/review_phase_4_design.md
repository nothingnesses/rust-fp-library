# Adversarial Review of the Phase 4 Dual-Row Scoped-Effects Design

## Summary

Phase 4 stores scoped operations as concrete constructors holding their action as a `Run<R, S, A>` value plus single-shot `Box<dyn FnOnce>` closures. The shape is heftia-compatible at the constructor level, but the plan never specifies how the per-constructor interpreter trait method gets to recursively process the stored action while the first-order handler list is still in scope; without that machinery, the design cannot deliver the "intercept `Throw` inside `action` before the outer handler discharges it" semantics that decisions.md actively claims over freer-simple's interposition. Counts: **2 fundamental**, **6 major**, **8 minor** findings. The single most important issue is **F1**: the scoped-effect interpreter trait shape is unspecified at exactly the load-bearing point. The design is **workable with revisions**; it does not require a different core encoding for the v1 set (`Catch`, `Local`, `Bracket`, `Span`), but Phase 4 will need to specify a parallel `DispatchScopedHandlers` shape that exposes (and lets handlers locally rewrite) the surrounding first-order handler list, which is non-trivial work the plan currently elides.

## Fundamental Flaws

### F1. The scoped-handler trait shape is unspecified at the load-bearing decision: how does a scoped handler intercept first-order effects inside its stored action?

- **Where:**
  - [plan.md:2015-2017](../../plan.md#L2015-L2017) (entire spec for the scoped-effect interpreter trait): "Scoped-effect interpreter trait. Method per constructor; fixed `Run<R, A>` continuation".
  - [decisions.md:481](../../decisions.md#L481): "_Interpreter continuation type._ Decision: fixed `Run<R, A>`. The trait method that interprets a scoped effect returns a `Run<R, A>`".
  - [decisions.md:470-474](../../decisions.md#L470-L474) (the property the design promises): "_vs freer-simple's interposition_: interposition only supports _first-order_ rewrites... It does not support true higher-order effects like `Error.catch` that need to pattern-match on exceptions thrown by the sub-computation. The port needs `Error.catch`, so interposition is insufficient."
  - Heftia source verbatim, [`heftia-effects/src/Control/Monad/Hefty/Except.hs:50-51`](../../../../../effects/heftia/heftia-effects/src/Control/Monad/Hefty/Except.hs#L50-L51):
    ```
    handleCatch :: forall e es. (Throw e `In` es, FOEs es) => Catch e ~~> Eff es
    handleCatch (Catch action hdl) = action & interposeInWith \(Throw e) _ -> hdl e
    ```
    The handler receives `action` as a complete `Eff es` value and uses `interposeInWith` to splice a `Throw` catcher _into_ that sub-program's effect interpretation, not after it.
- **What:** The plan documents the constructor payloads (`Catch<'a, E>` carries `action: Run<R, S, A>` and `handler: Box<dyn FnOnce(E) -> Run<R, S, A>>`) and says the interpreter has "one method per constructor", but never describes the method's signature. The crucial absent decision is: does `dispatch_catch` receive only the `Catch` value, or does it also receive a handle to the surrounding first-order handler list? Heftia's `handleCatch (Catch action hdl) = action & interposeInWith \(Throw e) _ -> hdl e` only works because the handler can _replace_ the `Throw` clause inside `action`'s interpretation. In the Rust port's current substrate, the FO handler list is consumed inline by [`Run::interpret`](../../../../fp-library/src/types/effects/run.rs#L552-L568)'s outer loop and is not threaded into per-layer dispatch in any way; [`DispatchHandlers::dispatch`](../../../../fp-library/src/types/effects/interpreter.rs#L141-L180) is invoked from inside that loop with no escape hatch for a scoped handler to rewrite the list.
- **Why fundamental:** [decisions.md:470-474](../../decisions.md#L470-L474) explicitly rejects freer-simple-style interposition because "interposition only supports first-order rewrites" and "the port needs `Error.catch`". The design positions itself as delivering more-than-interposition. If the eventual interpreter trait method takes only the `Catch` constructor, then the catch dispatcher's only options are (a) recursively `interpret` the `action` with the same handler list (in which case `Throw` is discharged by the outer `Throw` handler before `Catch` ever sees it; the `handler: FnOnce(E)` is _unreachable_); (b) pattern-match on the `Run<R, S, A>` tree itself looking for `Throw` constructors to splice (this _is_ heftia's interposition, but it requires either traversing the freer-monad's stored continuations or building a dedicated `interpose` primitive on each Run wrapper, neither of which is sketched). Without specifying which path Phase 4 takes, the plan has not shown that its design delivers the semantics decisions.md commits to. Per the rubric ([algebraic_effects.md:294-298](../algebraic_effects.md#L294-L298)) "Scoped operations" is a higher-order capability the plan claims to support; without a credible interpreter shape, that claim is unbacked. This rates fundamental because the missing piece is not a local detail; supplying it requires substrate machinery (handler-list interposition, or substrate-level program rewrites) that does not exist in Phase 1-3.
- **Worked example:**
  ```rust
  // Phase 4 program: Throw is in the FO row; Catch is in the scoped row.
  let outer_handlers = handlers! {
      ExceptBrand<MyErr>: |op: Except<MyErr, _>| match op {
          Except::Throw(e, _) => /* discharge: e.g., terminate program */,
      }
  };
  let scoped_handlers = scoped_handlers! { /* catch dispatcher */ };
  let prog: Run<ExceptRow, CatchRow, i32> = catch(
      throws_inside(),                       // action: Run<ExceptRow, CatchRow, i32>
      |_e: MyErr| Run::pure(0),              // recovery
  );
  prog.interpret_with_scoped(outer_handlers, scoped_handlers);
  // Question the plan does not answer: when interpret encounters
  // Node::Scoped(Catch{action, handler}), what does it do?
  // Option (a): recurse on action with outer_handlers. Then the Throw
  //   inside action is discharged by the FO handler above; the
  //   recovery `handler: FnOnce(MyErr)` is never called. Catch is a
  //   no-op.
  // Option (b): structurally rewrite the handler list to swap the
  //   Throw clause for one that returns to a Catch sentinel value;
  //   recurse on action; project sentinel back. This is heftia
  //   semantics. The plan does not describe the rewrite mechanism.
  // Option (c): walk action's tree directly, replacing Throw nodes
  //   with handler invocations. This requires a generic `interpose`
  //   primitive on each of the six Run wrappers; not in Phase 1-3,
  //   not sketched in Phase 4.
  ```
  Per [research/deep-dive-scoped-effects.md:22](../../research/deep-dive-scoped-effects.md#L22), heftia's actual `handleCatch` is option (b)/(c) hybrid via `interposeInWith`. The plan stores everything heftia stores (action as data, handler as data), but never says which dispatch path the trait method takes. This is the load-bearing missing detail.

### F2. `Box<dyn FnOnce>` body closures plus default `Run`/`RunExplicit`'s non-`Clone` action structurally preclude any user-defined scoped effect that needs to run the body or the action more than once.

- **Where:**
  - [plan.md:1992-1998](../../plan.md#L1992-L1998) (Bracket Val flavour): `body: Box<dyn FnOnce(A) -> Run<R, S, (A, B)>>`, `release: Box<dyn FnOnce(A) -> Run<R, S, ()>>`.
  - [plan.md:1983](../../plan.md#L1983) (Catch): `handler: Box<dyn FnOnce(E) -> Run<R, S, A>>`.
  - [plan.md:1985-1989](../../plan.md#L1985-L1989) (Local Val/Ref): `modify: Box<dyn FnOnce(E) -> E>` / `Box<dyn FnOnce(&E) -> E>`.
  - Substrate: [`Run::peel`](../../../../fp-library/src/types/effects/run.rs) wraps `Free`, which is non-`Clone` for the default Box-based variant. The action stored in `Catch::action: Run<R, S, A>` is therefore single-shot on `Run` and `RunExplicit`. Multi-shot wrappers (`RcRun`, `ArcRun`, `RcRunExplicit`, `ArcRunExplicit`) make `Run<R, S, A>` `Clone`, so the action becomes structurally re-runnable, but the user-supplied closures inside the constructor remain `FnOnce`.
  - Heftia source: [`heftia/src/Data/FTCQueue.hs:38-40`](../../../../../effects/heftia/heftia/src/Data/FTCQueue.hs#L38-L40) defines the type-aligned queue continuation; bodies stored as `m a` (e.g., `Catch e :: m a -> (e -> m a) -> Catch e m a`) are interpreted by handlers that may invoke them zero, once, or many times.
  - Concrete heftia multi-shot body example: [`heftia-effects/Example/Continuation/Main.hs:38-41`](../../../../../effects/heftia/heftia-effects/Example/Continuation/Main.hs#L38-L41):
    ```
    applyResetFork numberOfFork (ResetFork m) =
        m & interposeBy pure \Fork resume -> do
            r <- mapM resume [1 .. numberOfFork]
            pure $ mconcat r
    ```
    Here `resume` is invoked `numberOfFork` times, each producing a complete sub-result that is concatenated; this is a user-defined scoped effect (`ResetFork :: f w -> ResetFork f w`, line 33-35) and is exactly the shape the plan's `define_scoped_effect!` macro promises to support.
- **What:** The plan ships v1's standard scoped set (`Catch`, `Local`, `Bracket`, `Span`) using single-shot closures, which is correct for those four; classic catch / local / bracket / span all run their body once. But [decisions.md:482](../../decisions.md#L482) explicitly commits to user-extensibility ("Per-effect boilerplate (one struct + one impl per scoped effect) can be reduced later via a `define_scoped_effect!` macro") and [plan.md:2018-2021](../../plan.md#L2018-L2021) ships the macro in Phase 4 step 4. Any user who tries to define a scoped effect requiring a multi-shot body, e.g.:
  - **Coroutine** (heftia-effects' `Coroutine.hs`): yield repeatedly; resumption captures the body multiple times.
  - **Provider**: run the body once per offered resource.
  - **NonDet-as-scoped** with backtracking-aware bracket: re-run a sub-program per choice.
  - **Retry**: re-run on transient failure.
    ...will hit the `Box<dyn FnOnce` wall. On the multi-shot Run wrappers the action _value_ is `Clone`, but the recovery / body closures are not, so even with `RcRun` the user cannot cleanly write a "run body twice with different inputs" effect. There is no documented path to multi-shot bodies.
- **Why fundamental:** Fixing requires changing the closure type at the constructor level (e.g., `body: Rc<dyn Fn(...)>`) and likely the substrate (closure storage cells must be `Clone`-friendly, which conflicts with the existing default Box-based Free's bind contract; see [`Run::bind`](../../../../fp-library/src/types/effects/run.rs#L310-L315) which already takes `FnOnce`). The asymmetry surfaces in the prior review's M7 ([review_effects_rs.md:391-401](../0_first_order_effects_implementation/review_effects_rs.md#L391-L401), unresolved) and metastasises here: every scoped effect that the user might want to extend the framework with inherits the single-shot ceiling. The plan's "user-defined scoped effects" is a partial guarantee, not a full one, and the partial scope is not enumerated. Per the rubric ([algebraic_effects.md:177](../algebraic_effects.md#L177)) "_continuation flexibility_" is exactly the expressiveness gap algebraic effects open over MTL; this design closes the gap for the v1 set and re-opens it for any scoped effect user-extensibility would deliver. This is fundamental in the encoding sense: the `FnOnce` choice and the non-`Clone` default action are not local plan revisions; they touch the substrate.
- **Worked example:** Suppose a user wants `Retry<E, A>` that re-runs an action up to N times if it throws. A heftia-faithful Rust signature would want:
  ```rust
  pub struct Retry<'a, E, A> {
      pub action: Run<R, S, A>,                              // re-runnable
      pub on_failure: Rc<dyn Fn(E, usize) -> Decision + 'a>, // multi-shot
  }
  ```
  but the plan's documented closure shape forbids `Fn` closures in scoped constructors (every example uses `FnOnce`), and on default `Run` the action itself is not `Clone`, so the second retry attempt would consume the original. Heftia delivers `Retry`-style effects via `Coroutine` ([effects/heftia/heftia-effects/src/Control/Monad/Hefty/Coroutine.hs](../../../../../effects/heftia/heftia-effects/src/Control/Monad/Hefty/Coroutine.hs)) trivially because the FTCQueue continuation is shareable. The Rust port has no equivalent.

## Major Issues

### M1. Phase 4 must rewrite all six Run wrappers' interpret methods to lift the `S = CNilBrand` invariant, but the plan does not sketch the new public signature.

- **Where:**
  - [plan.md:2015-2017](../../plan.md#L2015-L2017) (interpreter trait spec): one bullet, no signatures.
  - Existing constraint: [`Run::interpret`](../../../../fp-library/src/types/effects/run.rs#L552-L568) at lines 552-568 is bound to `Run<R, CNilBrand, A>`, mirrored across [`run_explicit.rs`](../../../../fp-library/src/types/effects/run_explicit.rs), [`rc_run.rs`](../../../../fp-library/src/types/effects/rc_run.rs), [`arc_run.rs`](../../../../fp-library/src/types/effects/arc_run.rs), [`rc_run_explicit.rs`](../../../../fp-library/src/types/effects/rc_run_explicit.rs), [`arc_run_explicit.rs`](../../../../fp-library/src/types/effects/arc_run_explicit.rs).
  - The `Node::Scoped(cnil) => match cnil {}` arm at [run.rs:565](../../../../fp-library/src/types/effects/run.rs#L565) closes the case structurally; lifting it requires a real branch.
- **What:** Phase 4 either (a) keeps the existing single-list `interpret` for `S = CNilBrand` and adds a parallel `interpret_scoped` taking two handler lists, or (b) generalises `interpret` to take both lists and degrades to single-list when `S = CNilBrand`. The plan picks neither. Each option has API consequences (existing call sites that pass one list might break under (b); doctests and examples need to be reworked under (a)). On the Erased-family (single-shot consumption) the rewrite is mechanical; on the Explicit family, the type-level row plumbing for the second list interacts with the existing HRTB-poisoning workarounds at [arc_run.rs](../../../../fp-library/src/types/effects/arc_run.rs) (`unwrap_first`, `lift_node`, `make_node_first`, `wrap_first_arc`, `unwrap_pure_node`).
- **Why major (not fundamental):** The interpret-method shape is a local API decision that does not require changing the core encoding. Phase 4 can sketch it; the plan just hasn't.

### M2. The Val/Ref split for `Bracket` and `Local` makes the scoped row carry up to three constructors per logical effect; mixing flavours in one program is a 2x-3x row tax not analysed.

- **Where:**
  - [plan.md:1976-2014](../../plan.md#L1976-L2014) (Val/Ref ship side by side: `Bracket`, `RefBracket<P>`; `Local`, `RefLocal`; `RefBracket` further splits over `P: RefCountedPointer`).
  - [decisions.md:497](../../decisions.md#L497): "`bracket`'s Ref impl additionally carries the pointer brand `P` so that `Ref<RcBrand>` and `Ref<ArcBrand>` are distinct dispatch impls".
- **What:** A user who calls `bracket(...)` twice in the same program with two different closure shapes (one taking owned `A`, one taking `Rc<A>`) gets two distinct scoped-row entries (`Bracket<File, _>` and `RefBracket<RcBrand, File, _>`). If they also use `local`, that adds two more (`Local<E>`, `RefLocal<E>`). The minimum row size for "use both flavours of bracket and both flavours of local" is four constructors plus tail, not two. [decisions.md:483-499](../../decisions.md#L483-L499) frames this as "uniform with the existing Val/Ref dispatch pattern", but the existing pattern in [`fp-library/src/dispatch/`](../../../../fp-library/src/dispatch/) is one trait with two _impls_ on one type; here the row gets two _types_, which is a different cost. The plan does not analyse the row-size cost or mention that the macro user must declare every flavour they intend to use.
- **Why major (not fundamental):** The cost is real but not encoding-level. Users can be told "declare what you use", and the dual-row macro can lexically-sort the resulting longer row. The cost is ergonomic and discoverability-oriented, not soundness-affecting.

### M3. `Box<dyn FnOnce>` for `release` plus the absence of any panic-safety statement means resource cleanup is not guaranteed if `body` panics.

- **Where:**
  - [plan.md:1995-1998](../../plan.md#L1995-L1998) (Bracket): "the interpreter moves the returned `A` into `release`". Implicit: this only happens if `body` returns; on panic, the move never executes.
  - [decisions.md:485-489](../../decisions.md#L485-L489) (rationale for Val flavour): no mention of panic.
  - Rubric: [algebraic_effects.md:304-308](../algebraic_effects.md#L304-L308) lists "Resource safety" with the explicit warning "_genuinely subtle: nondeterministic backtracking past a bracket is a known semantic minefield_".
  - Heftia comparison: heftia does **not** ship a `Bracket` effect at all; resource safety is delegated to GHC RTS exceptions through the `UnliftIO` higher-order effect ([`heftia-effects/src/Control/Monad/Hefty/Unlift.hs:21-22`](../../../../../effects/heftia/heftia-effects/src/Control/Monad/Hefty/Unlift.hs#L21-L22)) and explicitly warns ([`heftia-effects/Example/Stream/Main.hs:27-31`](../../../../../effects/heftia/heftia-effects/Example/Stream/Main.hs#L27-L31)) that pure algebraic-effects state (interrupted continuations, `runChoose` backtracking, etc.) does not trigger `bracket` cleanup; only `IO`-level termination does.
- **What:** The plan stores `body` and `release` as separate single-shot closures. The interpreter pattern is "run body to completion, get `(A, B)`, move the returned `A` into release". In Rust, if `body` panics during interpretation (the user's code panics, an arithmetic overflow trips, an `unwrap` hits `None`), unwinding never reaches the post-body release call. The `body` closure has already been consumed (the `FnOnce` was called), but the `release` closure hangs in the scoped-effect node, dropped at unwind without being invoked. PureScript's `bracket` ([Aff.purs:308](https://github.com/purescript-contrib/purescript-aff/blob/master/src/Effect/Aff.purs#L308), the source decisions.md cites for inspiration) relies on `Aff`'s built-in async-exception masking; the plan inherits Rust's drop-based model, which would require `release` to live in a `Drop` impl on a guard. The plan does not describe such a guard.
- **Why major (not fundamental):** Closeable by either (a) wrapping body invocation in `std::panic::catch_unwind`, (b) constructing a `Drop`-implementing guard around the resource so `release` runs in `Drop`, or (c) explicitly documenting that bracket is panic-leaky and users must opt out of panics for resources they care about. Each is a local implementation choice. The plan is silent.

### M4. Bullet 6 ("Standard handlers ... wired through the dual row") obscures whether existing FO handlers gain scoped clauses or whether parallel scoped handlers are introduced; the two are structurally different.

- **Where:**
  - [plan.md:2046-2048](../../plan.md#L2046-L2048): "Standard handlers (`run_reader`'s `local` clause, `run_except`'s `catch` clause, etc.) wired through the dual row."
  - [decisions.md:455](../../decisions.md#L455): "Each scoped effect is a concrete constructor holding its action and handler(s) as first-class values. Interpreters dispatch on the constructor via a trait with one method per variant".
- **What:** "`run_reader`'s `local` clause" reads as if `run_reader` (today an FO handler for `ReaderBrand` per [reader.rs](../../../../fp-library/src/types/effects/reader.rs)) gains a clause for the scoped `Local`. But the dual-row architecture's whole point is that scoped constructors are interpreted by a _separate_ trait. So `run_reader` for the FO Reader effect and a parallel `run_reader_scoped` (or whatever the trait impl is called) for `Local`/`RefLocal` are two different things, dispatched at two different layers of the interpreter loop. The bullet is at minimum imprecise; the reader is left to guess whether the FO and scoped handlers share state (an environment, an exception holder) or are independent.
- **Why major (not fundamental):** Specifying which is fine plan work. But "FO and scoped share state" is a load-bearing question for Local: the local handler must temporarily modify the env that the FO Reader handler returns, which is a state-share. The plan doesn't establish how that state is shared.

### M5. The `'a` lifetime parameter on every scoped constructor (`Catch<'a, E>`, `Local<'a, E>`, etc.) is structural cost on Erased-family wrappers where it has no observable role.

- **Where:**
  - [decisions.md:480](../../decisions.md#L480): "Each scoped-effect constructor is generic over a lifetime `'a` (`Catch<'a, E>`, `Local<'a, E>`, etc.) from day one, mirroring corophage's per-effect `'a` already adopted by section 4.1 Option 4 for first-order effects."
  - [plan.md:1982-2014](../../plan.md#L1982-L2014) carries `'a` on every constructor.
- **What:** The Erased family (`Run`, `RcRun`, `ArcRun`) requires `A: 'static` per the Phase 1-3 substrate's existing constraints; their `Run<R, S, A>` is `'static`-bounded and the inner `Box<dyn FnOnce>` closures are `'static + ...`. On Erased, the `'a` parameter has no inhabitant other than `'static`; it appears in signatures but does no work. Only on the Explicit family (`RunExplicit`, `RcRunExplicit`, `ArcRunExplicit`) does `'a` carry a non-`'static` lifetime that the body closures might want to borrow over. The plan parameterises uniformly, paying the cost on Erased for symmetry.
- **Why major (not fundamental):** Cosmetic on Erased; the parameter is not unsound. But the existing Phase 3 effects (`Reader<E, A>`, `Except<E, A>` in [reader.rs](../../../../fp-library/src/types/effects/reader.rs), [except.rs](../../../../fp-library/src/types/effects/except.rs)) ship without `'a` on the Erased path (they take `'a` only when wrapped via `RcCoyoneda` etc.), so the dual-row scoped row is _less uniform_ with the FO row, not more. Calling out the asymmetry would help users.

### M6. Interaction with `interpret_with` (row-narrowing) is unspecified for the scoped row.

- **Where:**
  - Existing FO row narrowing: [`Run::interpret_with`](../../../../fp-library/src/types/effects/run.rs#L885-L900) takes one effect, narrows the row, returns a `Run<RMinusE, CNilBrand, A>`.
  - Phase 4 plan: no parallel row-narrowing primitive on the scoped row.
- **What:** With dual rows, "narrow one effect at a time" can target FO or scoped effects. The pipeline interpretation pattern (the existing M-target stack-safety story per [run.rs:824-833](../../../../fp-library/src/types/effects/run.rs#L824-L833) tells users to chain `interpret_with` calls then end with `interpret_rec`) becomes ambiguous with two rows: when does scoped narrowing happen? If the scoped row is narrowed first, scoped handlers may need access to FO effects that haven't been removed yet (Local needs Reader::Ask). If FO is narrowed first, scoped handlers may run after their target FO effect is gone. The plan does not specify an ordering or a primitive shape (`interpret_scoped_with::<EBrand>` analog).
- **Why major (not fundamental):** The omission is a plan-detail gap. Either ordering is workable; the interaction needs to be specified before the doctests for Phase 4 can be written.

## Minor Issues

- [decisions.md:481](../../decisions.md#L481) says "fixed `Run<R, A>`" for the trait return type, but the Phase 4 constructor table at [plan.md:1982-2014](../../plan.md#L1982-L2014) carries `Run<R, S, A>`. Whether the trait method drops `S` from its return (because the scoped layer is the one being discharged) or keeps `S` (because the recovery program may include further scoped operations) is not consistent across the two documents.
- [decisions.md:495](../../decisions.md#L495) admits "`Span`: no closure to dispatch over" yet places `Span<'a, Tag>` in the scoped row alongside operations that genuinely need higher-order treatment. `Span` is structurally a metadata-attached FO operation (operate on a sub-program, do nothing semantic). Putting it in the scoped row means every scoped-handler interpreter trait grows a `dispatch_span` method that just recurses on the action. The cost is small but the placement is over-specified.
- [plan.md:2018-2021](../../plan.md#L2018-L2021) introduces `define_scoped_effect!` and a `scoped_effects!` macro that "shares the lexical-sort helper with Phase 2's `effects!`". The plan does not say whether the lexical sort sorts FO and scoped brand identifiers in the same namespace (they likely shouldn't), or how the macro disambiguates a name collision (`Reader` vs `RefLocal` look very different but `Local` vs a user-defined `LocalState` could conflict).
- [decisions.md:483](../../decisions.md#L483) calls Val/Ref dispatch "uniform with the existing Val/Ref dispatch pattern" but the existing pattern at [`fp-library/docs/dispatch.md`](../../../../fp-library/docs/dispatch.md) routes _one_ trait operation through two impl markers; the scoped Val/Ref split here ships _two_ struct types into the row, which is a different shape. The framing is misleading.
- [plan.md:1992-1998](../../plan.md#L1992-L1998) (Bracket Val) requires the user's body to return `(A, B)`, threading the resource back through the type. This is unusual; normal bracket bodies return `B`. The thread-back is documented in [decisions.md:485](../../decisions.md#L485) but it puts a Rust-specific deviation in a heftia-positioned API and the test surface for Phase 4 step 7 ([plan.md:2049-2052](../../plan.md#L2049-L2052)) does not mention covering the thread-back idiom in doctests.
- "Heftia-inspired" vs actual heftia: [resolutions.md:1893-1906](../../resolutions.md#L1893-L1906) acknowledges the row-encoding divergence (heftia uses one list with `KnownOrder`-per-element; the port uses two rows) but the same acknowledgment does not appear in [decisions.md:436](../../decisions.md#L436) or in [plan.md:1970](../../plan.md#L1970)'s Phase 4 header. Readers of decisions.md or the plan get the "direct port" framing; only readers who reach resolutions.md see the divergence note.
- The interpreter loop's `Node::Scoped` arm currently closes via `match cnil {}` ([run.rs:565](../../../../fp-library/src/types/effects/run.rs#L565)); the prior review's [F3 / M8](../0_first_order_effects_implementation/review_effects_rs.md#L119-L172) noted that the dual-row API surface is paid for in every signature even though the second row is uninhabited. Phase 4 is the resolution to that, but the ergonomics-during-Phase-4-development concern (every doctest passes `CNilBrand` for the scoped slot until Phase 4 ships) is not addressed.
- The plan's bullet 7 ("Tests: scoped-effect unit tests covering each of the four standard constructors plus `compile_fail` cases") does not enumerate _which_ negative cases are covered. The Phase 3 `compile_fail` tests covered three layers (single-shot rejection of multi-shot ops, brand-row mismatch, missing-handler). Phase 4 negative cases worth covering include: scoped operation in an FO-only row, mismatched body and release closure shapes for Bracket dispatch, `RefBracket` with a non-`RefCountedPointer` `P`. None of these are listed.

## Comparison to Existing Scoped-Effect Designs

The proposed design is closest to **polysemy** with a heftia-flavoured row separation, not to heftia itself.

- **Polysemy**: scoped operations are encoded as first-order constructors carrying an action and handler closures (`Catch :: m a -> (e -> m a) -> Error e m a`). Handlers use the `Tactical` environment to manipulate the action under an existential functor `f ()`. _The proposed design's constructor shape (`action: Run<R, S, A>`, `handler: Box<dyn FnOnce(E) -> Run<R, S, A>>`) maps onto polysemy's almost cell-for-cell, except that the action lives in a separate row instead of the FO row._ Problems inherited: scoped handlers cannot easily intercept FO effects mid-flight without explicit interposition machinery; the dispatch shape is a per-constructor trait method rather than a structural rewrite.
- **Heftia**: scoped operations are reified data nodes that elaborators rewrite via `interposeInWith`. The proposed design borrows the row separation but not the elaboration mechanism. Problems inherited from heftia: open extension story (the plan promises it, the encoding partially delivers it). Problems _not_ inherited because not adopted: substrate-level multi-shot continuations, shareable continuation queues for body replays.
- **fused-effects**: tagless-final carrier composition with a separate `Algebra (h :+: r) m` for higher-order operations. Inherited: nothing structurally; the proposed design is data-tree based, not carrier-based.
- **freer-simple**: interposition only, no scoped-effect first-classness. [decisions.md:474](../../decisions.md#L474) explicitly rejects this. _Problem the proposed design might silently re-inherit_: if F1's missing piece (interpreter shape that supports interposition into the action) is filled by "just recurse with the same handler list", the design degrades to freer-simple's ceiling, which decisions.md says is insufficient.
- **extensible-effects**: row-encoded multi-effect free monads predating freer/heftia. Inherited: the per-bind allocation cost of any free-monad-encoded substrate, mitigated by Phase 3 step 5e's [`RcCatList`/`ArcCatList`](../../../../fp-library/src/types/rc_cat_list.rs) for the multi-shot wrappers.

**Novel problems specific to this design (not present in the comparison family):**

- The Val/Ref split for `Bracket` and `Local` is a Rust-specific axis driven by the absence of GC; heftia and polysemy don't have it. The cost is row-size bloat for users who mix flavours (M2).
- The `(A, B)` thread-back idiom for Bracket Val is Rust-specific; heftia bracket uses straight `body :: a -> Eff es b` with GC aliasing the resource. Worked example in [decisions.md:528-540](../../decisions.md#L528-L540).
- The dual-row `Run<R, S, A>` type with the second row pinned to `CNilBrand` until Phase 4 ships is a Rust-port-specific structural tax (M5 plus prior review's [M8](../0_first_order_effects_implementation/review_effects_rs.md#L403-L418)).

**Heftia scoped effects the design would not be able to port without revising F2:**

- `Coroutine.hs` (yield + resume): needs multi-shot body.
- `Provider.hs`: needs body replay.
- `Unlift.hs`: needs the body to escape into an outer `IO`-like context with reentry.
- Scoped `NonDet` with backtracking: needs body re-execution per choice.

These are out of scope for v1 per the plan's enumeration, but the framing "user-defined scoped effects via `define_scoped_effect!`" implies user-extensibility that does not actually cover this region of the design space. The boundary is not documented.
