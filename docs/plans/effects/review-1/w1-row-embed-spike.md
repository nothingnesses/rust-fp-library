# W1 Row Embed Spike: Structural Widening Feasibility

This spike checks whether `expand` / `weaken` can be implemented as a
sound structural widening of the first-order row `R` and scoped row `S`
across the six Run wrappers.

## Result

Recommendation: proceed with W1, but implement row widening as
representation-aware structural traversal, not as unsafe coercion and not
as a direct `Free::hoist_free` / `NaturalTransformation` wrapper.

Row widening is feasible, but two constraints shape the implementation:

- The row evidence is specific to the payload type being embedded. A
  generic `NaturalTransformation<NodeBrand<R, S>, NodeBrand<R2, S2>>`
  cannot add the needed per-call `CoproductEmbedder` bounds to
  `transform<'a, A>`, because the trait method signature is fixed.
- Default `Run` has private scoped-boundary frames that keep
  single-shot continuations outside selected scoped branches. An
  implementation that lowers those frames through public `Free::resume`
  / `Free::to_view` before branch selection can distribute a `FnOnce`
  continuation through a `Functor::map` call, which is the exact behavior
  the boundary representation avoids.

No user-facing decision is needed before implementation. The adopted
approach is to build a crate-private row-embed helper with method-local
embedding evidence and to make default `Run` use its raw-step /
boundary-frame machinery.

## Approach 1: unsafe or layout coercion

PureScript can expose an O(1) `expand` by relying on representation
coercion. That is not sound for Rust's current row encoding:
`CoproductBrand<A, CNilBrand>` and
`CoproductBrand<A, CoproductBrand<B, CNilBrand>>` resolve to different
enum layouts, sizes, and drop behavior.

Trade-offs:

- Pro: minimal runtime cost.
- Con: unsound across different `Coproduct` shapes and not defensible in
  safe Rust.

Recommendation: reject. W1 should stay O(n) and structural.

## Approach 2: `NaturalTransformation` plus `hoist_free`

The tempting implementation is a natural transformation from
`NodeBrand<R, S>` to `NodeBrand<R2, S2>` and then `hoist_free` on the
underlying Free family.

Trade-offs:

- Pro: reuses existing Free-family traversal for simple free-backed
  programs.
- Pro: matches the mathematical shape of changing only the functor.
- Con: the existing `NaturalTransformation` trait cannot express the
  required per-`A` `CoproductEmbedder` evidence on its fixed
  `transform<'a, A>` method.
- Con: for default `Run`, `hoist_free` goes through public stepping,
  which can attach a single-shot continuation through row functor
  mapping before a scoped branch is selected.

Recommendation: do not use this as the W1 implementation base. The idea
is useful as a mental model, but the Rust trait and default `Run`
representation constraints make it the wrong abstraction.

## Approach 3: method-local row embed plus raw-step traversal

Define a crate-private row-embed helper whose method carries the
`CoproductEmbedder` evidence for the concrete payload type at the call
site. Then use that helper when rebuilding each observed node:

- First-order layers map inner programs from the source wrapper to the
  target wrapper, then embed the source row into the wider first-order
  row.
- Scoped layers map inner programs the same way, then embed the source
  scoped row into the wider scoped row.
- Default `Run` uses `RunRepresentation` / `RunScopedBoundaryFrame`
  methods that inspect raw steps, transform raw scoped layers, and
  rewrite continuation queues without forcing selected scoped actions
  through the public `Free::to_view` path.
- Explicit, Rc, and Arc wrappers can use their public one-step
  decomposition where it preserves their continuation semantics, or
  generated helper code can emit the same structural traversal directly.

Trade-offs:

- Pro: sound for different row layouts and preserves default `Run`'s
  single-shot boundary invariant.
- Pro: keeps the first-order row and scoped row widening symmetric.
- Pro: the method-local evidence keeps the required `CoproductEmbedder`
  bounds at the concrete payload type where Rust can check them.
- Con: more implementation code than `hoist_free`, especially for the
  default erased wrapper and Arc `Send + Sync` projection bounds.
- Con: the public surface should still be generated by W2 so this does
  not become six hand-maintained copies.

Recommendation: adopt this approach.

## Approach 4: explicit / Rc / Arc only fallback

If the default erased wrapper hits an unresolvable type-system or safety
limit, ship `expand` / `weaken` on the Explicit, Rc, and Arc families and
document the default `Run` limitation.

Trade-offs:

- Pro: still unblocks row composition for the wrappers whose structure is
  easier to traverse.
- Con: creates a public capability asymmetry around the default wrapper,
  which is the wrapper most users are likely to start with.
- Con: makes examples and generated docs more conditional.

Recommendation: keep this as the fallback only. The raw-step /
boundary-frame path appears sufficient, so the default plan remains
all-six-wrapper support.
